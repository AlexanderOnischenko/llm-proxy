Она не знает, кто и зачем меняет приоритеты.

Пример 1 — “Система перестаёт зависать под нагрузкой”
До (без Feature 1)

100 запросов приходят одновременно

Все попадают в одну FIFO очередь

1 долгий запрос в начале блокирует всё

Tail latency взрывается

SLA не соблюдается

После (только Feature 1)

Есть 3 фиксированные очереди: high, normal, low

Все запросы по умолчанию идут в normal

Concurrency = 10

Очередь high зарезервирована, даже если сейчас пуста

👉 Функциональный эффект:

Если в систему позже приходит high-запрос (внутренний, системный, health-check, warmup и т.п.) —
он гарантированно не ждёт, даже если normal забита.

Система больше не “залипает” под burst-нагрузкой.

📌 Это уже новое поведение системы, даже если:

клиент не выбирает приоритет,

админ ничего не крутит,

метрик нет.

Пример 2 — “Отмена запроса реально освобождает ресурсы”
До

Клиент отправил запрос

Клиент передумал

Запрос висит в очереди / inflight

Ресурсы сожраны зря

После (Feature 1)

Каждый запрос имеет lifecycle:

accepted → queued → inflight → done | cancelled

Очередь умеет:

убрать запрос

освободить слот

корректно перепланировать следующие

👉 Функциональный эффект:

Cancel перестаёт быть “best effort”

Очередь реально реагирует на отмену

Средняя latency под нагрузкой падает

📌 И снова — без admin API, без динамики, без мониторинга.
