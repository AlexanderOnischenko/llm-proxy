# Feature: Priority Execution Engine

## Problem Statement
Фича вводит детерминированный, наблюдаемый и лимитированный цикл исполнения admitted-запросов в однопроцессном runtime. После внедрения становится истинным утверждение: «каждый принятый запрос либо выполняется в строгом приоритетном порядке с соблюдением inflight‑квот и max_queue, либо отклоняется предсказуемым кодом overflow; слоты захватываются и освобождаются согласованно независимо от исхода, а cache/dedup подключается в фиксированной точке цикла».

## Users / Actors
- Исполнитель очереди (PriorityChatQueue + worker loop) — основной владелец цикла.
- Клиентские роутеры (`/v1/chat/completions`, `/v1/chat/invoke`, `/llm`) — ставят задачи и получают предсказуемые отклики/коды.
- Cache/Dedup слой — разделяет повторяющиеся запросы и использует кэшированное выполнение.
- Observability/metrics — потребляет события очереди/исполнения для метрик и алертов.
- Control plane (ConcurrencyConfigManager) — поставляет лимиты, но не управляет индивидуальными задачами.

## Use Cases
- Последовательное обслуживание admitted-запросов с приоритетами P1…Pn и ограниченными слотами, исключающее переполнение inflight и дублирующий захват слотов.
- Корректное возврат 429 overflow при отсутствии буфера (`max_queue == 0`) либо переполнении глобальной очереди.
- Поддержка cache/in-flight dedup в определённой фазе цикла без нарушения лимитов и FIFO порядка.
- Безопасная обработка отмен: удаление queued задач или фиксация cancelled исхода для inflight, всегда с освобождением слота.
- Экспорт детерминированных событий (enqueue/dequeue/outcome) для метрик и снимков без влияния на планирование.

## Feature Boundary & Responsibility
- Фича владеет Execution Loop: `dequeue → захват слота → выполнение handler (с cache/dedup по выбранной политике) → фиксация outcome → освобождение слота → планирование следующего`.
- Принимает решения только о порядке извлечения и захвате/освобождении слотов; не решает admission, нормализацию запроса, выбор приоритета или изменение лимитов.
- Является фича-применителем: использует заданные лимиты/приоритеты и поставляет гарантии соблюдения конкурентности и очереди; не переопределяет политику control plane или admission.
- Обязана эмитить события для наблюдаемости (латентности, overflow, исходы), но не определяет продуктовые метрики.

## Execution Phase
Доминирующая фаза — Execution в однопроцессном loop после admission и до egress. Фича активируется после того, как запрос принят и поставлен в очередь, и завершает влияние в момент фиксации outcome и освобождения слота. Изменения control plane применяются атомарно между циклами, но не пересматривают уже запущенные задачи.

## Conceptual Inputs & Outputs
- **Входы:** admitted задачи с приоритетом и payload, карта лимитов (slots_by_priority, max_queue, default_priority), события отмены, сигналы shutdown, политики cache/dedup.
- **Выходы:** выбранный next job, корректно захваченные/освобождённые слоты inflight, outcomes (success/error/cancel/overflow) с кодами, события для метрик (queue_wait, provider_latency, overflow), read-only snapshot очереди.

## Proposed Solution
- **Чёрный ящик исполнения:** Worker читает приоритетные FIFO очереди, выбирает первый приоритет с queued задачами и свободным слотом, увеличивает inflight, выполняет handler (с выбранным размещением cache/dedup), фиксирует outcome и освобождает слот в `finally`.
- **Backpressure:** Глобальный `max_queue` ограничивает суммарный `queued`; при `max_queue == 0` разрешается только немедленное исполнение при наличии свободного слота, иначе запрос отклоняется 429 без постановки. Пер-приоритетные капы рассматриваются отдельно.
- **Cancellation:** Queued-cancel удаляет задачу до исполнения (если возможно) и уменьшает queued; inflight-cancel фиксирует исход `cancelled`, останавливает/дожидается handler и освобождает слот.
- **Cache/Dedup:** Фиксируется точка подключения (см. ADR): либо до очереди (минимизация нагрузки и shared future), либо внутри handler (простота и защита очередью). В обоих случаях дедуп использует канонический provider payload и не кэширует ошибочные upstream ответы (или кэширует — решение в ADR).
- **Observability:** Каждое событие enqueue/dequeue/outcome/overflow обновляет метрики; snapshot отражает согласованность `queue_len` и `in_flight` с реальными структурами.

## Feature Interfaces
- Внутренние:
  - `enqueue(request_id, priority, payload, endpoint) -> Future/Result` — ставит задачу с учётом `max_queue`.
  - Execution loop API для handler: `handler(payload) -> provider_response` с интеграцией cache/dedup.
  - `snapshot() -> QueueState` — read-only состояние очереди и inflight.
- Внешние контрактные эффекты:
  - HTTP ответы: 429 `queue_overflow` при нарушении max_queue, 500 `provider_error` для ошибок апстрима, 499/`ClientClosed` для cancel (или аналогичный код/лог).
  - Метрики/события: queue_wait, provider_latency, overflow, outcomes по приоритетам.
- Зависимости: потребляет лимиты из ConcurrencyConfigManager и канонический priority claim из admission; не изменяет их.

## Rules and Invariants
- Strict priority: выбирается первый приоритет с queued>0 и свободным слотом; внутри приоритета — FIFO. Возможная starvation низких приоритетов фиксируется ADR.
- Inflight counter по каждому приоритету не уходит в отрицательные значения; queued gauge соответствует фактической длине структур.
- Слот захватывается один раз перед запуском handler и освобождается в `finally` независимо от исхода (success/error/cancel/shutdown).
- При `max_queue == 0` состояние `queued > 0` недопустимо; при `queued_total >= max_queue` новые задачи отклоняются 429 без изменений счётчиков inflight.
- Любой admitted запрос завершится outcome (success/error/cancel) или будет явно dropped на shutdown по правилам завершения; двойное освобождение слота запрещено.
- Порядок выбора задач детерминирован при одинаковой последовательности событий; кэш/дедуп не нарушает FIFO внутри приоритета.
- Cancellation никогда не оставляет занятый слот после фиксации исхода.
- Метрики обновляются на enqueue/overflow/start/end; пропуск событий считается нарушением контракта observability.

## ADRs
- **Strict-priority vs fairness:** Базовый режим — строгий приоритет без aging; starvation низких приоритетов допускается. Альтернативный round-robin/aging требует отдельного ADR и смены правил dispatch.
- **Cache placement:** Предпочтительный вариант фиксируется: A) внутри handler (проще, очередь защищает провайдера, но не разгружает буфер) или B) перед enqueue с shared future для dedup (уменьшает нагрузку, усложняет контракт очереди). Выбранный вариант должен быть единственным в реализации.
- **Dedup error policy:** Ошибки апстрима не кэшируются (или кэшируются с TTL) — решение фиксируется явно; дедуп разделяет идентичные запросы по каноническому payload.
- **Cancel policy:** queued-cancel разрешён и удаляет задачу; inflight-cancel фиксирует outcome cancelled и освобождает слот; отсутствие поддержки queued-cancel должно быть явно задокументировано как риск нагрузочного расхода.
- **Overflow mapping:** overflow отдаёт 429/`queue_overflow`; provider ошибки — 500/`provider_error`; cancel — 499/`ClientClosed` (лог/ответ).

## Non-Goals / Out of Scope
- Изменение приоритетов, лимитов или нормализации priority claim — зона admission/control plane.
- UI/UX клиента, SDK и форматирование ответов поверх кодов/заголовков.
- Многопроцессная/распределённая очередь; фича опирается на однопроцессный инвариант.
- Автоматическое ретрай или повторное планирование после ошибки провайдера.
- Политика аутентификации/авторизации для admin/metrics путей.

## Open Questions
- Какой вариант размещения cache/dedup выбираем сейчас (A внутри handler или B до enqueue) и требуется ли гибридный режим?
- Должны ли ошибки апстрима кэшироваться с отрицательным TTL для защиты провайдера или всегда обходить кэш?
- Требуется ли per-priority `max_queue` поверх глобального, и как оно сочетается со strict priority?
- Как сигнализировать starvation низких приоритетов (метрика/алерт) при строгом приоритете?
- Нужен ли soft shutdown protocol (drain) с тайм-аутом для корректного завершения inflight без приёма новых задач?
