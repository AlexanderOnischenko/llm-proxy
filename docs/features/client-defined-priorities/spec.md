# Feature: Client-Defined Priorities

## Problem Statement
Дать клиентам контролируемый способ влиять на относительный приоритет своих запросов через API, сохраняя валидность приоритетов и совместимость с внутренней очередью.

## Users / Actors
- Клиентские приложения, вызывающие `/v1/chat/completions` и `/v1/chat/invoke`.
- Внутренние интеграции через `/llm`, которые должны передавать или наследовать приоритет.
- Приоритетная очередь (`PriorityChatQueue`), применяющая нормализованный приоритет при admission.

## Use Cases
- Клиент задаёт `X-Priority: p1`, чтобы ускорить критичный запрос.
- Клиент не указывает приоритет и получает безопасный дефолт из конфигурации.
- Интеграция через `/llm` пробрасывает приоритет тела/заголовка в очередь без ручной маппинга.

## Feature Boundary & Responsibility
Фича отвечает за приём, валидацию и нормализацию заявленного приоритета клиента в совместимый с очередью идентификатор. Она не меняет лимиты, конкурентность или планирование — только переводит клиентский ввод в каноническое значение.

## Execution Phase
Admission / Scheduling (выбор/нормализация приоритета перед постановкой в очередь).

## Conceptual Inputs & Outputs
### Inputs (conceptual)
- HTTP метаданные: заголовок `X-Priority` или поле `priority` в теле запроса (строковое значение).
- Конфигурация очереди: список допустимых приоритетов и дефолт (`PriorityChatQueue.priorities`, `default_priority`).
- Правила маппинга псевдонимов (`highest`/`p0` → старший приоритет, `lowest` → младший).

### Outputs (conceptual)
- Канонический приоритет из множества, поддерживаемого очередью.
- Ошибка 400 при невалидном значении или отключённом приоритете (0 слотов).
- Передача канонического приоритета в вызов `PriorityChatQueue.enqueue(...)`.

## Proposed Solution

### Affected Components
- `llm.routers.chat` — парсить `X-Priority` или `priority` в теле, применять псевдонимы, валидировать наличие в `queue.priorities`, использовать `default_priority` по умолчанию.
- `llm.routers.llm` — при трансляции LangChain‑запросов пробрасывать/нормализовать приоритет теми же правилами.
- `PriorityChatQueue` — источник допустимых приоритетов и дефолта; при отсутствии слотов для приоритета возвращает overflow/ошибку.

### Data Models
- Используется: `ChatCompletionRequest` — хранит входной `priority` (опционально) для `/v1/chat`.
- Используется: карта приоритетов и слотов из `Settings.llm_priority_limits_map` (через построенный `PriorityChatQueue`).
- Требуется новая сущность: `PriorityMapping` (логический концепт) — таблица псевдонимов и дефолтов (`highest`/`p0`/`lowest` → реальные ключи очереди).

### Interfaces
- Public API: заголовок `X-Priority`, поле `priority` в теле `/v1/chat/completions` и `/v1/chat/invoke`; поле приоритета в `/llm` адаптируется теми же правилами.
- Internal: `_parse_priority(...)` в роутере использует `queue.priorities`/`default_priority` и `PriorityMapping`.

### Integration Notes
- Граничит с `Dynamic Concurrency Control`: если приоритет имеет 0 слотов после обновления лимитов, попытка использовать его должна приводить к отказу до постановки в очередь.
- Граничит с `Queue Observability`: метрики и headers отражают канонический приоритет; псевдонимы не должны появляться в метриках.
- Не меняет payload для провайдера; только метаданные для диспетчера.

### Feature Interfaces
- Потребляет гарантии от: настроек очереди (множество приоритетов, дефолт, слоты), роутеров, обеспечивающих уникальный `request_id`.
- Поставляет гарантии: валидированный приоритет для admission; ошибки 400 при неизвестных/отключённых приоритетах; детерминированное сопоставление псевдонимов.

## Rules and Invariants
- Если приоритет не указан — используется `default_priority` из очереди.
- Псевдонимы `highest`/`p0` маппятся на первый доступный приоритет, `lowest` — на последний; остальные значения должны точно соответствовать `queue.priorities`.
- Приоритет, отсутствующий в `queue.priorities` или с нулевым слотом, приводит к отказу (400/429 в зависимости от стадии).
- Нормализованный приоритет передаётся неизменным в метрики и заголовки ответа.
- Правила одинаковы для `/v1/chat/*` и `/llm` маршрутов.

## ADRs
- Приоритет задаётся клиентом через HTTP‑метаданные, нормализуется на входе и хранится в виде внутреннего ключа очереди.
- Псевдонимы ограничены фиксированным набором (`highest`/`p0`/`lowest`) для простоты и предсказуемости.

## Non-Goals / Out of Scope
- Изменение лимитов конкурентности или порядка планирования (контроль другой фичей).
- Автоматическое “aging” или перераспределение приоритетов во времени.
- UI/дашборды; наблюдаемость остаётся в `Queue Observability`.

## Open Questions
- Нужны ли дополнительные псевдонимы (например, `urgent`/`bulk`) или достаточно минимального набора?
- Следует ли логировать исходное значение приоритета для аудита, даже если оно маппится в дефолт?
