# Feature: Dynamic Concurrency Control

## Problem Statement
Обеспечить управляемое во времени изменение бюджета конкурентности по приоритетам без рестарта процесса так, чтобы каждое новое admission‑решение использовало актуальные лимиты и не нарушало выполнение уже принятых запросов.

## Users / Actors
- SRE/операторы и автоматизированные runbook‑агенты, формирующие намерение изменить бюджет.
- Control plane API (`admin/routers/concurrency`), принимающее и валидирующее изменение.
- Планировщик `PriorityChatQueue`, потребляющий новый бюджет при принятии запросов.
- Наблюдатели (метрики/снимки), читающие текущее состояние бюджета и очереди.

## Use Cases
- При инциденте оператор уменьшает слоты для низких приоритетов и освобождает ёмкость под `p1` без рестарта.
- Автоматизация повышает суммарную конкурентность после добавления ресурсов.
- Временное отключение приоритета (0 слотов) для шумных клиентов с немедленным отказом их запросов.

## Feature Boundary & Responsibility
- Фича принимает и валидирует операторские изменения бюджета, версионирует состояние и атомарно передаёт его в `PriorityChatQueue`.
- Не решает, какой приоритет выбрал клиент/маршрутизация; не изменяет политику нормализации приоритетов.
- Не управляет метриками или UI; наблюдаемость использует существующие источники очереди.
- Не делает самостоятельных решений о деградации — только применяет переданное намерение, если оно валидно.

## Execution Phase
Control plane действует асинхронно относительно основного потока: изменения бюджета происходят до admission будущих запросов и не затрагивают уже выполняющиеся. Доминирующая фаза — Admission/Scheduling (через обновление бюджетов), доступная только до начала нового решения о приёме.

## Conceptual Inputs & Outputs
### Inputs
- Намерение оператора/автоматизации: желаемые слоты по приоритетам, опционально дефолтный приоритет и причина изменения.
- Базовая конфигурация из `Settings` (стартовый бюджет и ограничения по приоритетам).
- Текущее состояние очереди (inflight/queued) — для проверки применимости уменьшения слотов.

### Outputs
- Версионированное состояние Concurrency Budget (слоты по приоритетам, default, max_queue, источник изменения).
- Решения admission, основанные на последней версии бюджета (принятие, отказ по отсутствию слотов, отказ по неизвестному/отключённому приоритету).
- Диагностические сигналы: ошибки валидации (400), конфликты применимости (409), журнал событий изменения.

## Proposed Solution
- `ConcurrencyConfigManager` хранит единственный источник правды о бюджете, инициализированный из `Settings`, поддерживает версию/метаданные и валидирует вход.
- Admin API (`GET/PATCH /admin/concurrency`) выступает единственной точкой записи/чтения бюджета: принимает намерение, проверяет допустимость приоритетов и невозможность сократить слоты ниже текущего inflight, возвращает новое состояние или объяснимую ошибку.
- При успешном применении `ConcurrencyConfigManager` атомарно передаёт обновлённое состояние в `PriorityChatQueue`, после чего все новые admission‑решения используют одну и ту же версию бюджета.
- Observability читает бюджет через `ConcurrencyConfigManager`/`PriorityChatQueue.snapshot()` без возможности его изменять; метрики очереди остаются неизменными.
- В случае рестарта процесс реконструирует начальное состояние из `Settings`; восстановление более свежей версии — предмет отдельного решения (см. Open Questions).

## Feature Interfaces
- Admin control plane: `GET /admin/concurrency` (read‑only текущая версия бюджета), `PATCH /admin/concurrency` (применить изменение; 200 на успех, 400 на валидационные ошибки, 409 на невыполнимость из‑за inflight).
- Внутренний контракт: `ConcurrencyConfigManager.apply_update` выдаёт новое состояние и одновременно обновляет `PriorityChatQueue.update_limits`; `get_state` предоставляет read‑only снимок для observability.
- Сигналы аудита: структурированный лог записи изменения (версия, источник, старое/новое состояние, причина/комментарий).

## Rules and Invariants
- Бюджет хранится в единственном экземпляре на процесс; отсутствие синхронизации между несколькими воркерами является явным ограничением.
- Все слоты по приоритетам — неотрицательные; приоритет с нулём считается отключённым и не может стать default.
- Default priority всегда принадлежит множеству приоритетов с положительной вместимостью и присутствует в бюджете.
- Попытка уменьшить слоты до значения, меньшего текущего inflight для любого приоритета, отклоняется (409) без изменения бюджета.
- Применение обновления атомарно: после успешного `apply_update` все новые admission‑решения видят одну версию бюджета; одновременные запросы к API получают согласованную версию.
- Версия бюджета монотонно увеличивается на каждое успешное изменение; текущее состояние доступно для чтения без блокировки.
- Ошибки admin API (400/409) не влияют на уже выполняющиеся запросы и не меняют состояние бюджета.
- `max_queue` и правила переполнения остаются неизменными, даже если слоты скорректированы.

## ADRs
- Control plane реализован в памяти поверх однопроцессного сервиса; горизонтальный шардинг/репликация вне объёма фичи.
- Обновление бюджета через API предпочтено перезапуску: минимизирует время недоступности и сохраняет метрики/очередь.
- Версионность и логирование изменения считаются обязательными для трассируемости operator intent → admission behavior.

## Non-Goals / Out of Scope
- Поддержка многопроцессного или распределённого запуска; синхронизация между процессами не решается.
- Автоматическое масштабирование по метрикам; фича применяет только явное намерение операторов/скриптов.
- Управление UI, dashboard или экспорт новых метрик сверх существующих показателей очереди.
- Изменение политики выбора приоритета клиентом или нормализации входных псевдонимов.
- Изменение `max_queue` в рамках того же API (остаётся статичным по `Settings`).

## Open Questions
- Нужна ли персистентная точка правды (файл/БД) для восстановления бюджета после рестарта вместо возврата к `Settings`?
- Требуются ли дополнительные механизмы аутентификации/авторизации и аудита для admin API, и какие роли их задают?
- Должен ли API позволять атомарно менять `max_queue` вместе с слотами, если появится потребность в управлении глубиной очереди?
