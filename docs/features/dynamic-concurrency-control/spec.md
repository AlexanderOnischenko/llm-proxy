# Feature: Dynamic Concurrency Control

## Problem Statement
Дать операторам возможность динамически изменять лимиты конкурентности по приоритетам без рестарта сервиса, чтобы защищать апстрим и управлять деградациями в реальном времени.

## Users / Actors
- Операторы/SRE, выполняющие ручные или автоматические runbook‑действия.
- Планировщик `PriorityChatQueue`, который применяет новые лимиты при принятии запросов.
- Клиентские приложения — косвенно, через изменившееся поведение при приёме/отказе.

## Use Cases
- Оператор снижает слоты низкого приоритета (`p3`), чтобы освободить ёмкость под `p1` во время инцидента.
- Автоматический скрипт увеличивает общую конкурентность при добавлении ресурса без рестарта контейнера.
- SRE временно отключает приоритет (0 слотов), чтобы предотвратить падение апстрима из‑за шумных клиентов.

## Feature Boundary & Responsibility
Фича управляет конфигурацией конкурентности очереди на уровне control plane: приём и валидация новых лимитов, применение их к `PriorityChatQueue`, публикация текущего состояния. Она не принимает решения о выборе приоритета запросом и не отвечает за наблюдаемость или UI.

## Execution Phase
Admission / Scheduling (управляет параметрами планировщика; действует из control plane, но эффект проявляется в приёме/диспетчере).

## Conceptual Inputs & Outputs
### Inputs (conceptual)
- Административные команды/запросы с желаемыми слотами по приоритетам и (опционально) общим лимитом.
- Базовая конфигурация из `Settings` (`llm_priority_limits_map`, `llm_priority_default`, `llm_queue_max_len`) как стартовое состояние.
- Текущее состояние очереди (inflight/queue) для проверки применимости лимитов.

### Outputs (conceptual)
- Актуальная `ConcurrencyConfig` (версионированная карта слотов по приоритетам) в памяти процесса.
- Решения admission: новые запросы принимаются или отклоняются согласно обновлённым лимитам и правилам приоритетов.
- Сообщения об ошибках при невалидных изменениях (400/409) без прерывания текущих запросов.

## Proposed Solution

### Affected Components
- `PriorityChatQueue` — добавить возможность атомарного обновления карты слотов по приоритетам и дефолтного приоритета без пересоздания очереди.
- `llm.deps` — инициализировать очередь с базовой конфигурацией и передавать ссылку в control plane слой для обновлений.
- Новый компонент: `ConcurrencyConfig` manager (in‑memory) — хранит текущую карту слотов, версию и источник изменения; валидирует вход.
- Новый HTTP роутер: admin API `/admin/concurrency` — чтение/изменение лимитов (PATCH/GET), возвращает актуальное состояние и версию.

### Data Models
- Используется: `Settings.llm_priority_limits_map` — стартовая карта слотов по приоритетам.
- Требуется новая сущность: `ConcurrencyConfig` — держит `slots_by_priority`, `default_priority`, `max_queue`, `version`, `updated_at`, `updated_by` (источник/метка runbook).
- Требуется новая сущность: `ConcurrencyUpdateRequest` — входной административный запрос с частичными/полными значениями слотов и необязательной причиной изменения.

### Interfaces
- Admin HTTP API: `GET /admin/concurrency` (текущее состояние), `PATCH /admin/concurrency` (применить новые слоты; отвечает 200/400/409).
- Внутреннее API: `PriorityChatQueue.update_limits(new_limits, default_priority=None)` — атомарное применение лимитов; не прерывает текущие inflight.
- Событие/лог: запись факта изменения (версия, старые/новые значения, инициатор) в журнал приложения.

### Integration Notes
- Граничит с `Client-defined Priorities`: допустимые приоритеты должны совпадать с объявленными; отключение приоритета (0 слотов) должно вести к отказу ещё до очереди.
- Граничит с `Queue Observability`: метрики inflight/queue остаются источником наблюдаемости; отдельные метрики этой фичи не требуются.
- Control plane действует в одном процессе (архитектурный инвариант сервиса); масштабирование через несколько воркеров не поддерживается.
- При уменьшении слотов ниже текущего inflight новые запросы блокируются/отклоняются, но уже выполняющиеся доводятся до конца.

### Feature Interfaces
- Потребляет гарантии от: статической конфигурации `Settings`, определения приоритетов в маршрутах (`llm.routers.chat`), однопроцессного режима.
- Поставляет гарантии: актуальные лимиты конкурентности для приёма/диспетчера, отказ при недопустимых приоритетах или переполнении очереди.

## Rules and Invariants
- Карта слотов не может содержать отрицательных значений; приоритеты с нулевым слотом считаются отключёнными и приводят к отказу при выборе.
- Default priority всегда принадлежит множеству приоритетов с положительной вместимостью.
- Суммарная конкурентность не может быть снижена ниже текущего inflight; если запрос на уменьшение нарушает это условие — возвращается 409 с бездействием.
- Обновление лимитов атомарно: все обращения к `PriorityChatQueue` после успешного применения видят одну и ту же версию `ConcurrencyConfig`.
- `max_queue` и правила overflow остаются неизменными и применяются поверх обновлённых слотов.
- Любой отказ в admin API не влияет на уже выполняющиеся запросы и не изменяет текущую конфигурацию.

## ADRs
- Динамика конкурентности реализуется через control plane поверх существующей `PriorityChatQueue`, без перезапуска приложения и без изменения data plane API.
- Хранение конфигурации в памяти оправдано однопроцессным режимом; при появлении нескольких воркеров потребуется внешний стор (не входит в фичу).

## Non-Goals / Out of Scope
- UI или dashboards для управления конкурентностью.
- Автоматическое масштабирование по метрикам; только ручные/скриптовые изменения.
- Выбор приоритета клиентом и политика нормализации приоритетов.
- Расширение метрик сверх уже существующих queue/inflight/latency.

## Open Questions

- Требуется ли аутентификация/авторизация для `/admin/concurrency`, и какие роли допускаются?
- Следует ли разрешить изменение `max_queue` в рамках той же фичи или оставить его статичным из `Settings`?
