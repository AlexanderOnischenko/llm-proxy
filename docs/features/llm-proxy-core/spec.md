# Feature: LLM Proxy Core Priority Admission & Execution Tracking

## Problem Statement
Сделать приём и исполнение LLM‑запросов детерминированными по приоритетам: каждый запрос получает канонический приоритет, атомарное решение о принятии/отказе и измеряемый путь исполнения в однопроцессном планировщике без скрытых потоков конкурентности.

## Users / Actors
- Клиентские приложения, использующие `/v1/chat/completions` и `/v1/chat/invoke`.
- Интеграции через `/llm` (LangChain‑совместимые клиенты).
- Операторы/SRE, контролирующие конкурентность и деградации через метрики и административные эндпоинты.

## Use Cases
- Получить ответ даже под нагрузкой за счёт явного или выведенного приоритета и прозрачной очереди.
- Отправить запрос через `/llm`, наследуя те же правила приоритета и лимитов, что и публичные маршруты.
- Наблюдать глубину очереди, inflight и задержки, чтобы вовремя корректировать Concurrency Budget.

## Feature Boundary & Responsibility
Фича — решатель Admission/Scheduling: нормализует приоритет, сопоставляет его с Concurrency Budget, принимает или отклоняет запрос, создаёт Request Identity и отдаёт измеримое исполнение. Она не принимает решений о политике приоритетов (источник — Settings/Control Plane), не изменяет Concurrency Budget сама и не отменяет уже принятые запросы.

## Execution Phase
Доминирующая фаза: Admission/Scheduling. Нормализация завершена до входа в фичу; Observability — read‑only отражение принятых решений и исходов.

## Conceptual Inputs & Outputs
**Inputs**
- Canonical Chat Request (валидация и запрет stream завершены ранее).
- Priority Claim из заголовка/тела + псевдонимы.
- Текущее Concurrency Budget (слоты по приоритетам, default_priority, max_queue, версия источника).
- Очередное состояние: занятость слотов, глубина очереди.
- Состояние кэша/провайдера (для исполнения после приёма).

**Outputs**
- Admission Decision: принятие с request_id или отказ (400 для некорректного приоритета/stream, 429 при переполнении).
- Request Identity, сквозной для ответа, метрик и логов.
- Execution Telemetry: queue latency, provider latency, inflight/queue gauges, overflow/error counters.
- Клиентский Response Envelope: ответ провайдера + `x-llm-proxy-*` заголовки; для `/v1/chat/invoke` — метрики также в теле.

## Proposed Solution
- **Admission as deterministic gateway.** Приоритет извлекается и нормализуется через PriorityMapping против актуального Concurrency Budget от ConcurrencyConfigManager. Только приоритеты с положительной вместимостью допускаются; неизвестные/нулевые — немедленный 400.
- **Queueing semantics.** В однопроцессном PriorityChatQueue поддерживаются слоты inflight и общая глубина очереди. `max_queue == 0` разрешает приём только при наличии свободного слота; `max_queue >= 0` ограничивает суммарную очередь всех приоритетов, иначе 429 `queue_overflow`.
- **Execution with identity.** Принятый запрос получает request_id, ставится в очередь с пометкой endpoint и каноническим приоритетом, выполняется через OpenAIChatProvider с общим кэшем. Освобождение слота обязательно после фиксации исхода (успех/ошибка).
- **Observability surface.** Prometheus‑метрики и admin snapshots (`/metrics`, `/admin/queue`) читают состояние очереди и исходы без модификации. Заголовки и тело (для invoke) возвращают queue/provider задержки и приоритет.
- **Failure handling.** Ошибки валидации/приоритета → 400; переполнение слотов/очереди → 429; ошибки провайдера → 500 `provider_error`. Многопроцессный запуск блокируется на старте, иначе инварианты слотов недействительны.

## Feature Interfaces
- **Consumes:** PriorityMapping (нормализация приоритета), ConcurrencyConfigManager (актуальный бюджет), Settings (дефолты модели/сэмплинга), Cache/Provider health.
- **Provides:** PriorityChatQueue (принятие/исполнение с метриками), HTTP маршруты `/v1/chat/completions`, `/v1/chat/invoke`, `/llm`, Observability endpoints `/metrics`, `/admin/queue`, Request Identity для логов/метрик.

## Rules and Invariants
- Каждый принятый запрос получает уникальный request_id; он отражён в ответе и метриках. Проверяемо через логи/метрики.
- Запрос не проходит Admission, если его приоритет отсутствует в Concurrency Budget или имеет вместимость 0. Проверяемо модульным тестом PriorityMapping и интеграцией очереди.
- При `max_queue == 0` запрос принимается только при свободном inflight слоте; иначе 429 без постановки. Покрывается интеграционным тестом очереди.
- Глубина общей очереди не превышает `max_queue` (при `>= 0`) вне зависимости от приоритета. Метрика overflow фиксирует нарушение.
- Slot accounting: захват слота перед исполнением, освобождение после завершения независимо от исхода. Проверяемо через инкремент/декремент inflight в метриках.
- Stream режим для чат‑маршрутов запрещён; попытка `stream=True` → 400. Проверяемо через отрицательный тест маршрутов.
- Очередь/метрики работают в одном процессе; обнаружение многопроцессного окружения приводит к отказу старта. Проверяемо стартовым чек‑листом.
- Observability эндпоинты не меняют состояние очереди или бюджетов. Проверяемо через отсутствие побочных эффектов в snapshot()/metrics.

## ADRs
- Однопроцессная модель — единственный способ корректно считать inflight/queue и предоставлять непротиворечивые метрики.
- Admission и Observability разделены: snapshot/metrics не могут влиять на планирование.
- Кэш/провайдер вызываются после принятия; queue не обходит кэш, чтобы Admission оставался быстрым и детерминированным.
- Общий PriorityChatQueue обслуживает публичные и LangChain маршруты, обеспечивая единое правило приоритета и лимитов.

## Non-Goals / Out of Scope
- Отмена запросов после приёма или в ходе исполнения.
- Автоматическая перераздача слотов при отказах провайдера.
- Изменение приоритетов или слотов самим фичером; все обновления приходят извне (Settings/Control Plane).
- Streaming‑ответы для чат‑маршрутов.
