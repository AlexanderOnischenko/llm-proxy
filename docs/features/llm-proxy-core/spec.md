# Feature: LLM Proxy Core Priority Admission and Execution Tracking

## Problem Statement
Обеспечить детерминированное принятие и выполнение LLM‑запросов в условиях конкуренции за ресурсы, сохраняя совместимость с OpenAI‑подобным API и предоставляя прозрачные метрики по приоритетам и задержкам.

## Users / Actors
- Клиентские приложения, отправляющие `POST /v1/chat/completions` или `/v1/chat/invoke`.
- Внутренние сервисы и интеграции, использующие `/llm` для LangChain‑совместимых вызовов.
- Операторы и SRE, контролирующие нагрузку и метрики очереди.

## Use Cases
- Клиент хочет гарантированно получать ответ даже при нагрузке, опираясь на конфигурируемые приоритеты.
- Интеграция через `/llm` нуждается в тем же контроле очереди и метриках, что и публичный endpoint.
- Операторы наблюдают за глубиной очереди, inflight и латентностью через `/metrics`, чтобы вовремя реагировать на деградацию.

## Feature Boundary & Responsibility
Фича отвечает за приём, нормализацию и планирование выполнения чат‑запросов через приоритетную очередь, а также за возврат ответов с метаданными выполнения. Она не принимает решений об изменении лимитов или приоритетов во время выполнения и не выполняет отмену запросов после приёма.

## Execution Phase
Admission / Scheduling

## Conceptual Inputs & Outputs
### Inputs (conceptual)
- HTTP‑запрос с телом `ChatCompletionRequest` (OpenAI‑совместимое) и необязательным `X-Priority` или `priority` в теле.
- Конфигурация очереди и кэша из `Settings` (лимиты по приоритетам, `default_priority`, `max_queue`, параметры провайдера и кэша).
- Текущее состояние очереди (inflight/queue) и кэшированные ответы провайдера.

### Outputs (conceptual)
- Решение о приёме или отказе (429 при переполнении, 400 при некорректных входах).
- Выполненный ответ провайдера, дополненный `request_id` и метриками очереди (в заголовках и, для `/v1/chat/invoke`, в теле).
- Обновлённые метрики Prometheus по очереди, inflight и результатам выполнения.

## Proposed Solution

### Affected Components
- `PriorityChatQueue` — управляет приоритетными слотами, глубиной очереди, измеряет задержки и обновляет метрики.
- `llm.routers.chat` — валидирует тело запроса, нормализует приоритет, ставит запросы в очередь и возвращает метрики.
- `llm.routers.llm` — адаптирует LangChain‑совместимые вызовы к `ChatCompletionRequest`, затем использует ту же очередь.
- `llm.services.chat_provider.OpenAIChatProvider` — вызывает upstream, применяя значения по умолчанию модели/temperature/top_p и общий кэш.
- `llm.deps` и `llm.main` — инициализируют singleton‑зависимости (кэш, провайдер, очередь) в единственном воркере.

### Data Models
- Используется: `ChatCompletionRequest` — нормализованное представление входного payload чата (messages, model, temperature, top_p, max_tokens, stop, stream).
- Используется: `QueueResult`/`QueueMetrics` — внутренние атрибуты выполнения (очередная задержка, латентность провайдера, приоритет, endpoint).
- Концепт: `request_id` — уникальный идентификатор запроса, возвращаемый клиенту и включённый в метаданные.

### Interfaces
- HTTP API: `POST /v1/chat/completions` (ответ + метрики в заголовках), `POST /v1/chat/invoke` (метрики также в теле), `POST /llm` (LangChain‑совместимый маршрут), `GET /metrics` (Prometheus).
- Queue API: `PriorityChatQueue.enqueue(request_id, priority, payload, endpoint)`, `snapshot()` для наблюдаемости.
- Config surface: поля `llm_priority_limits_map`, `llm_priority_default`, `llm_queue_max_len`, `llm_cache_*` из `Settings`.

### Integration Notes
- Работает в однопроцессном режиме; при старте проверяется отсутствие `PROMETHEUS_MULTIPROC_DIR` и многопроцессных конфигураций.
- Кэш SQLite шарится между провайдером и LangChain‑обёрткой; очередь не пытается обходить кэш — кэш выполняется на этапе вызова провайдера.
- Приоритеты должны соответствовать конфигурации; очередь отвергает приоритеты с нулевой ёмкостью.
- Ошибки провайдера проксируются как 500 с кодом `provider_error`, переполнение очереди — как 429 `queue_overflow`.

### Feature Interfaces
- Потребляет гарантии от: конфигурации лимитов (из control plane или окружения) и здоровья кэша/провайдера.
- Поставляет гарантии: стабильный `request_id`, соблюдение лимитов по приоритетам, измеримые задержки и метрики очереди для observability.

## Rules and Invariants
- Все запросы получают уникальный `request_id`; ответы включают заголовки `x-llm-proxy-*` с метриками очереди.
- Поддерживаются только приоритеты с положительной вместимостью; неизвестные или отключённые (0) приоритеты приводят к 400.
- Если `max_queue == 0` и слот занят, запрос немедленно отклоняется 429 без постановки в очередь.
- При `max_queue >= 0` переполнение общей очереди ведёт к 429 `queue_overflow`; глубина учитывается по всем приоритетам.
- `stream=True` в теле отклоняется 400; endpoint `/v1/chat/invoke` возвращает метрики также в теле.
- Лимиты inflight по каждому приоритету строго соблюдаются; свободный слот требует декремента после завершения задачи.
- Очередь и провайдер работают в одном процессе; многопроцессный режим запрещён стартовой проверкой.

## ADRs
- Единый воркер для корректной счётности очереди и метрик; запуск под многопроцессными обвязками запрещается на старте.
- Встроенный Prometheus‑слой для измерения задержек очереди, латентности провайдера, inflight и overflow.
- Кэш SQLite как общий слой дедупликации/TTL для всех входящих чат‑запросов, оборачивающий upstream вызовы.

## Non-Goals / Out of Scope
- Отмена запросов после постановки в очередь или во время выполнения.
- Динамическое изменение лимитов конкурентности/приоритетов без рестарта.
- Пользовательский контроль токенных лимитов на уровне прокси; контроль max_tokens отдан клиенту/провайдеру.
- Streaming‑ответы для чат‑маршрутов.

## Open Questions
- Следует ли применять значение `llm_max_tokens` из настроек как дефолт к запросам без `max_tokens`, чтобы унифицировать поведение?
- Нужна ли явная поддержка отмены запросов в очереди для долгих upstream‑вызовов, и кто будет источником управляющего сигнала?
